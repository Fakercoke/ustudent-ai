# 悉尼大学演示版改造、部署与简历投递计划

## 决策

课程原版先完整学到 **Lesson 10**，不要边学边改。完成评测与安全后，保存课程原版，
用 **1～2 个完整工作日**制作悉尼大学场景的最小可部署版本；然后进入 Lesson 11 部署，
部署成功后立即投简历。后续增强功能不阻塞投递。

推荐时间点：

```text
Lesson 7：RAG
Lesson 8～9：Agent + MCP
Lesson 10：评测 + 安全
        ↓
两天悉尼大学演示版改造
        ↓
Lesson 11：Docker + AWS 部署
        ↓
开始投简历，同时继续迭代
Lesson 12：监控、复盘、简历完善
```

---

## V1 的严格范围

V1 不是悉尼大学完整选课系统，只是一个可验证的作品集原型。

两天内只做：

- 一所大学：悉尼大学场景。
- 一个年份：例如 2026。
- 一个学位或专业方向。
- 5～8 门演示课程，保证 AI 资料与后端种子数据一致。
- 8～12 条课程规划、先修课、学分或退课规则。
- 中文和英文问答。
- RAG、Agent、MCP、安全、测试、Docker 与部署保持可用。
- 所有事实返回资料来源。
- 页面显著标记“个人作品集原型，非悉尼大学官方系统”。

V1 不做：

- 全校课程抓取。
- 所有专业和历年 Handbook。
- 墨尔本大学。
- 真实学生登录或真实选课。
- 自动同步学校网站。
- 大规模数据库重构。
- 为了赶进度而添加未经验证的规则。

- [ ] 课程原版所有 TODO 已完成。
- [ ] `pytest` 全部通过，并保存输出。
- [ ] Docker 本地可以构建和运行。
- [ ] 创建 Git 标签，例如 `course-complete`。

- [ ] 记录当前 Chroma 块数和关键接口样例，方便回归比较。
- [ ] 不直接修改或删除唯一能运行的课程版本。

## 第一天：让三层数据保持一致

目标：前端、后端数据库、RAG 不能分别讲三套不同的课程。

### 1. 先建立一张最小数据清单（1～2 小时）

每门演示课程只整理必要字段：

```text
course_code
course_name
credit_points
prerequisites
teaching_period
short_description
source_url
effective_year
```

每条学校规则记录：

```text
heading
summary
source_url
effective_year
accessed_date
```

要求：

- 使用公开资料，尽量用自己的摘要，不大量复制原文。
- 每条规则能追溯到来源。
- 不确定的内容明确标记，不让模型补全。

### 2. 更新后端模拟数据（1～2 小时）

- [ ] 用新的数据库迁移或课程提供的安全方式更新种子数据，不修改已执行迁移的历史含义。
- [ ] 只保留 5～8 门能完整演示的课程。
- [ ] 确认 `get_course` 返回的代码、名称和学分与 RAG 资料一致。
- [ ] 确认模拟 `enrol` 的成功与拒绝路径仍可测试。

如果后端更新超过 2 小时仍未跑通，立即缩小课程数量，不增加新功能。

### 3. 更新 AI 语料与品牌（2～3 小时）

- [ ] 替换 `data/handbook.md`。
- [ ] 替换 `data/faq.md`。
- [ ] 替换 `data/courses-catalog.md`。
- [ ] 修改生产代码中的 U+ 学校名称、虚构邮箱和兜底话术。
- [ ] 修改 Swagger/API 描述和对外 README。
- [ ] 保留历史课程材料中的 U+ 示例，不为全局替换而破坏教案记录。
- [ ] 增加非官方免责声明，不使用学校官方 Logo。

### 4. 重新建立 Chroma 索引（约 1 小时）

- [ ] 删除旧 collection 后重建，避免新旧数据混合。
- [ ] 检查块数、标题、来源和余弦距离配置。
- [ ] 手工搜索 5 个问题，确认没有召回旧 U+ 内容。
- [ ] 检查课程代码查询不会明显混入另一门课程。

### 第一天结束标准

```text
后端返回的课程 = RAG 描述的课程
RAG 中没有残留的 U+ 生产内容
Chroma 已重建
中文和英文各有一个问题能找到正确来源
```

## 第二天：评测、全栈验证、部署材料

### 1. 重写评测集（2～3 小时）

不要只把旧答案中的 `120 credits` 改成新数字。重新设计问题：

- [ ] 4～6 道明确有答案题。
- [ ] 2～3 道手册没有答案题。
- [ ] 1 道表面相关但实际没有答案的题。
- [ ] 1 道中文题。
- [ ] 1 道拼写错误题。
- [ ] 1 道短问题或含糊问题。
- [ ] 1 道精确课程代码题。

开发题与最终验收题分开。验收题在参数确定前不反复查看和调参。

### 2. 更新测试但不降低标准（1～2 小时）

- [ ] 更新依赖 U+ 固定文本的测试夹具。
- [ ] 不为了让测试变绿而删除失败测试。
- [ ] 保留结构化 `can_answer`、空响应、异常 JSON、中文拒答和降级测试。
- [ ] 增加“后端课程与 RAG 课程一致”的契约测试。
- [ ] 全部测试通过，记录新的测试总数。

### 3. 全栈冒烟测试（1～2 小时）

至少亲手演示：

```text
GET /health
POST /rag-ask：中文有答案
POST /rag-ask：英文有答案
POST /rag-ask：无答案并正确兜底
Agent → handbook_qa
Agent → get_course
Agent → enrol（模拟成功或明确拒绝）
MCP 工具至少调用一次
```

检查 `sources`、`used_fallback` 和 `degraded`，不能只看最终答案像不像正确。

### 4. Docker 与部署前检查（1～2 小时）

- [ ] 重新构建镜像，确保新 Chroma 索引进入镜像。
- [ ] 用全新容器启动，避免误用本机旧索引或缓存。
- [ ] 检查 `.env`、API key 和真实个人信息未进入 Git。
- [ ] 确认健康检查、启动时间和容器架构符合 Lesson 11 要求。
- [ ] 运行 `git diff --check` 和最终测试。

### 5. 准备投递材料（1～2 小时）

- [ ] README：项目目标、架构、运行方法、限制和免责声明。
- [ ] 一张完整架构图。
- [ ] 三张截图：RAG 回答、Agent 工具调用、自动评测。
- [ ] 一个可访问的部署地址。
- [ ] 一段 60 秒项目介绍。
- [ ] 三个真实排障故事：切块、阈值、拼写错误。
- [ ] 清楚标记课程 starter 与个人改进。

## 两天后的部署闸门

只有以下条件同时满足才部署：

- [ ] 生产代码和对外资料中没有误导性的 U+ 残留。
- [ ] AI 语料与后端课程数据一致。
- [ ] 所有自动测试通过。
- [ ] 新评测集中，有答案题能找到正确资料，无答案题能兜底。
- [ ] Docker 在全新环境中成功启动。
- [ ] 日志中没有 API key、学号、邮箱等敏感信息。
- [ ] 页面明确说明是非官方作品集原型。
- [ ] 已知不足写进 README，不宣称覆盖悉尼大学全部课程。

如果某个非核心增强未完成，不阻塞部署；把它放入部署后任务。

## 部署后立即投简历

部署完成后不等待“完美版本”，当天完成：

- [ ] 简历加入项目条目。
- [ ] GitHub/Bitbucket README 放部署地址和截图。
- [ ] 开始投递。
- [ ] 建一个公开的后续任务清单，让面试官看到项目仍在迭代。

建议项目名称：

```text
Sydney Course Planning Assistant — Portfolio Prototype
悉尼大学场景的可解释课程规划助手（非官方原型）
```

简历口径：

> Built and deployed a portfolio prototype for Sydney course-planning scenarios,
> combining FastAPI, Chroma RAG, a multi-tool LangGraph agent and deterministic
> backend APIs. Added bilingual query normalisation, structured abstention,
> source-level diagnostics and regression evaluation; clearly scoped the demo to
> a curated subset of public course information.

不要写：

```text
覆盖悉尼大学全部课程
悉尼大学官方选课系统
保证回答绝对正确
可以修改真实学生选课
```

## 部署后的渐进式更新

这些任务不阻塞第一轮投递。

### 第一优先级：让结果更可信

- 扩充真正未参与开发的盲测集。
- 增加资料年份、访问日期和来源链接。
- 增加改写前后查询与距离日志。
- 增加索引存在性和块数健康检查。

### 第二优先级：解决当前已知检索问题

- 对课程代码加入关键词检索或元数据过滤。
- 原问题与改写问题双路检索并融合。
- 对 `deadline` 等含糊问题返回澄清问题。
- 增加重排序，比较是否真的提升评测结果。

### 第三优先级：扩大产品能力

- 从 5～8 门课程扩大到一个完整专业方向。
- 增加入学年份隔离，避免新旧规则混用。
- 增加课程计划的“如果这样选会怎样”检查。
- 增加延迟、费用、失败率与降级次数监控。

### 最后再考虑

- 墨尔本大学适配器。
- 自动同步公开资料。
- 更完整的前端规划界面。
- 更大规模数据库与检索架构。

---

## 时间失控时的砍功能顺序

如果两天不够，按以下顺序砍，不要牺牲正确性和测试：

1. 砍课程数量，最低保留 5 门。
2. 砍复杂前端样式，保留 Swagger 或简单页面演示。
3. 砍额外 Agent 功能，保留课程规定、课程查询和一次模拟选课。
4. 砍自动数据同步。
5. 绝不砍来源、免责声明、测试和全新 Docker 环境验证。

核心原则：

> 先上线一个小而一致、能解释、能测试的版本；部署后边投简历边迭代，
> 不用“还不够完美”无限推迟投递。
